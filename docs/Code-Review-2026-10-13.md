# AudioPlayer 代码审查与局部简化（2026-10-13）

## 范围与结论

审查以 `5cfb92c` 为基线，覆盖全部应用源模块、WPF 绑定与资源、现有回归入口、发布脚本、忽略规则和文档。目标是提高职责清晰度并删除可以证明无作用的代码，保持公开接口、快捷键、算法、JSON 格式、用户文件和统一测试/发布入口。

现有应用规模适合具体类直接协作。核心模块没有明显框架式过度设计，没有发现需要立即修复的新产品正确性缺陷。实际改动集中在类内部职责、重复状态设置和不适用于本应用的脚本模板分支，不增加依赖或通用抽象。

## 发现的分类与实际变更

### 正确性所需

- 本轮没有确认新的产品行为缺陷；未以猜测增加保护、修改音频数学定义或改变配置恢复策略。
- 应用概述和文档索引原含其他应用的模板描述，容易使维护者误认 AudioPlayer 的依赖和职责。已改为本播放器的实际模块、用途和依赖，并把既有同日整改记录标为历史证据。

### 推荐的清晰度与维护改进（已实施）

- `AudioLibrary.LoadFolder` 原同时处理扫描、排序、逐文件标签读取及错误回退。将单文件读取留在同类的私有方法中，使目录流程与曲目流程可分别理解；返回数据、自然排序规则、非递归扫描和异常过滤保持一致。
- `AnalyzeAsync` 现在同时负责分析开始与结束的 UI 状态。首次加载和设置变更通过同一入口启动分析；加载替换音频前仍清除旧停顿结果，保证打开失败时不会保留旧导航数据。
- 设置读取只使用一个 `SilenceSettings` 对象。四个整数解析和有效范围校验不变；只有成功确认才应用返回值。
- `Publish.ps1` 与 `Test-Publish.ps1` 的 `$legacyDirectory = $null` 没有赋值或外部参数入口，旧目录迁移/冲突分支始终不执行。删除这些分支，并将只检查一个 EXE 的循环改成直接检查。
- `Test-PublishedApp.ps1` 的“是否启动创建配置”和“另一个集成项目”分别是固定 `true` 和 `null`。直接保留实际配置检查，删除不可达分支。重命名 EXE、含空格路径、配置定位和缺少 .NET 的验收保留。
- UI 测试必须先排队自动填写设置对话框，然后打开模态窗口；该 `Dispatcher.BeginInvoke` 不能提前等待。通过显式弃置返回值表达这一意图，未改变调度顺序。
- `.gitignore` 增加 `*.settings.json.bak` 与 `*.cache`，避免本地配置备份和可再生成缓存进入提交；保留现有音频、配置、构建、发布和测试报告忽略规则。

### 可选改动（未实施）

- 未拆成 MVVM、接口层或独立通知组件。窗口中的协调职责相互依赖，机械拆分会增加传参和导航成本。
- 未统一所有短方法、表达式属性、`var`、lambda 或模式匹配的写法。它们在当前代码中直接表达数据或类型检查，批量改写不解决实际问题。
- 两种数字输入检查、两个窗口提示以及默认参数重载保留少量重复，避免为几行代码建立共享基类或策略层。

## 保留复杂度的原因

- `AudioPlayer` 的 `SemaphoreSlim` 串行化打开、停止、定位等操作；`TaskCompletionSource` 确认当前播放周期的停止回调。设备状态可能先变为停止、之后才回调，不能直接删除等待或在事件到达前释放读取器。
- 设备回调不捕获 WPF 同步上下文，主窗口自行切回 Dispatcher；关闭等待活动操作、导航和后台分析，再关闭与释放播放器。
- 主窗口的导航队列保留快速连续左右键的顺序；拖动状态、分析状态和操作状态承担不同限制，不能简单合并。
- `RunCoreAsync` 集中把操作异常转成窗口提示，同时让被关闭流程等待的活动操作任务完成；直接将它替换为裸操作任务会改变关闭期间的异常路径。
- 自然排序按数字段长度与字符逐个比较，避免长文件名数字溢出；前导零处理和最后的名称比较有实际排序作用。
- PCM 分帧按绝对采样边界计算，避免非整数采样率的累积时长漂移；短读取补满与声道组校验保留。
- 配置的临时文件与 `File.Replace` 用于失败时保留原文件；JSON 与参数异常由 UI 明确报告，不静默覆盖损坏配置。
